# 独立自动更新程序的要求

本能力不可省略。按具体网站和系统生成并安装程序，采用可替换的输入、构建、部署、联网检测、服务与通知适配层。不要把某个案例的用户名、账号、分支、端口或脚本直接当成通用实现。

## 持久状态与处理顺序

建议状态：发现变更 → 等待写入稳定 → 校验 → 待完善 / 等待网络 / 可发布 → 构建 → 推送或上传 → 等待部署 → 线上确认 → 成功；永久错误进入需处理状态，服务另有 running / stopped / error。

保存批次标识、输入指纹、作品身份、最后有效版本、目标版本、重试计数、最后错误、用户是否收到反馈。重启不得清空预算、遗失未完成任务或把尚未上线的批次标成功。服务状态与最近发布状态分开记录；失败时保留公开的正常版本。

默认合并短时间多次保存；稳定等待的秒数根据文件类型及实测确定。一次仅处理一个发布批次。新内容取代未发布旧快照时明确标记被合并的批次，不让旧版本等待器因新版已上线误报失败。

程序只自动提交已约定素材范围。已有暂存内容、未经审阅的代码变更、错误分支/目标、远程冲突应停下给具体原因，不强制推送、不自行覆盖。所有网络与外部进程设置超时；并发互斥和遗留锁恢复依据进程是否真实存活。

## 断网恢复：自动继续与有限重试同时成立

不能沿用“同一文件指纹只尝试一次，失败后永不再试”的逻辑。输入未变化时，联网恢复也是重新调度事件。

可采用以下起点，再按部署服务调整并记录：

1. 已知离线时持久保存任务，进入 waiting_network，不不断执行上传。用本地网络事件或有界时长、低频的目标服务连通检查检测恢复。
2. 检测到网络稳定恢复后，自动恢复该批次，无需用户再编辑、重启或点击重试。
3. 一轮最多 3 次瞬时网络错误重试，带退避；同批最多一次自动恢复后的新一轮，总计最多 6 次实际上传尝试。计数跨重启保存。这个数字是可配置默认值，不是硬编码给所有服务的规则。
4. 网络抖动不能无限重置预算。预算耗尽后停止该批发布并通知原因和手动恢复入口；其他新任务按明确策略排队，不掩盖失败批次。
5. 权限失效、配置错误、冲突、内容校验失败不是断网，不能靠等网络反复尝试。要求对应修复后再处理。

长期等待网络与无限上传不同：任务可保持待处理，资源有限的网络监听继续存在；发布尝试仍有明确上限。首次进入等待网络要通知“本次尚未发布、联网后会继续”，长时间未恢复的提醒合并处理，不每次探测弹窗。恢复后的成功通知必须发出。

验收必须真正经历比当前重试窗口更长的断网：保持同一资料不变，恢复网络，观察程序自动继续并更新线上版本。手动 retry 的成功不能冒充这一项通过。

## 成功、失败与待完善的通知

同时保留可读日志及用户实际能收到的通知渠道。桌面通知可作为本地默认，但需确认权限；不可用时说明阻塞并安排用户同意的替代方式，不能只写日志就声称满足通知要求。

- 待完善：作品名、缺失/冲突字段、补齐方式；说明现有网页未被这次不完整更新覆盖。
- 等待网络/失败：受影响作品、已确认的具体原因、目前是否已推送、线上影响、下一步和详情入口。不能只给“更新失败”、堆栈或原始错误码。
- 成功：本次更新了什么、实际网址、确认时间/可追溯版本；只有部署成功且预期页面/版本已验证才发成功通知。
- 恢复：同一问题处理成功后，明确通知“已恢复并更新”。

示例：“《作品标题》还缺封面。请把图片放在说明.txt 所在文件夹；目前网页仍显示上一版本。”
示例：“资料已上传，但托管平台构建未通过。本次网页尚未更新，旧版仍可访问。查看详情中的构建原因，修正后会再处理。”

同一批次同一故障内部重试合并通知，不刷屏；原因变化或需要用户采取新动作时更新反馈。原始日志可作为详情，移除凭据和不必要私人信息。无法确定原因时如实写已知事实和下一步检查方法。

## 常驻服务与停止

交付一个与 Agent 无关的用户级服务，确认关闭聊天/终端后仍运行，并提供无需记住复杂命令的启动、停止、重试和状态入口（脚本快捷方式或适合系统的轻量入口）。最终也记录底层命令供维护者排查。

正常停止：停止接收新任务，妥善终止/等待当前本地工作，记录 stopped、通知用户，并按用户选择取消或保留登录启动。已经推送的云端工作可能继续，通知中须说明。重新启动时恢复持久待处理任务。

意外退出：监督程序或系统服务管理机制检测，记录 error 并通知；不要无限崩溃重启。状态查询核对进程/系统任务，不把昨天的 running 文件当成今天还在运行。整机断电、通知权限撤销或监督者自身被强杀时，不能承诺即时提醒；下一次启动/查询必须识别过期状态并记录。

## 发布与恢复

源码推送不等于发布。检查托管状态、线上版本标识和关键页面/资源；确定的失败与超时未确认区别记录。超时后云端可能完成，重新处理前先核对线上版本，避免重复发布或错误回退。

发布前保留最后有效内容/输出/版本，成功后原子切换；失败不覆盖旧站。恢复优先通过新提交还原需要的内容，不重写历史，不把用户后续修复一并覆盖。详细验收见 acceptance.md。
